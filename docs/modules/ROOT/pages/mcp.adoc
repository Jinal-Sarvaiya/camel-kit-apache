= MCP servers

Camel Kit uses the Model Context Protocol to verify Camel configuration, to guide Citrus test generation and to
search documentation without loading whole catalogs into the agent's context. `init` configures two local servers by default (three with `--with-citrus-mcp`;
released versions 0.4.1 and earlier include all three by default)
in the agent's MCP configuration file (see xref:agents.adoc[] for the file of each target); the agent starts each
one with JBang when a skill first needs it, and JBang resolves the runner and the catalog artifacts from the
configured repositories.

[cols="1,3"]
|===
| Server | Purpose

| `camel`
| The Apache Camel catalog: components, EIPs, data formats, languages, Kamelets and examples; route, YAML and
  configuration validation; diagnostics, migration and OpenAPI helpers

| `camel-knowledge`
| Hybrid search over indexed Apache Camel documentation, CVE advisories, release notes and Jira issues; see
  xref:knowledge.adoc[]

| `citrus`
| The Citrus action and endpoint catalogs, the YAML DSL schema and the test-authoring guidance used by `camel-test`
|===

The JBang runner coordinates of this release:

[subs="attributes+"]
----
camel            org.apache.camel:camel-jbang-mcp:{camel-version}:runner
camel-knowledge  io.github.luigidemasi:camel-kit-knowledge-mcp:{camel-kit-knowledge-version}:runner
citrus           org.citrusframework:citrus-mcp-server:{citrus-version}:runner
----

The generated configuration is, in the target's JSON or TOML shape:

[source,json,subs="attributes+"]
----
{
  "mcpServers": {
    "camel": {
      "command": "jbang",
      "args": [
        "--repos", "<configured MCP repositories>",
        "-Dcamel.catalog.repos=<configured catalog repositories>",
        "-Dquarkus.log.level=WARN",
        "-Dquarkus.http.port=-1",
        "org.apache.camel:camel-jbang-mcp:{camel-version}:runner"
      ]
    }
  }
}
----

Versions and repository lists come from `distribution.properties`; nothing is extracted into the project, and the
generated launch configuration is used unchanged. Targets with exact tool filtering receive the workflow allowlist
of each server from the workflow manifest; Codex CLI adds `default_tools_approval_mode = "prompt"`, Pi reads the
same `.mcp.json` through `pi-mcp-adapter`.

[[authority]]
== Responses are data

An MCP response is loaded context. The workflow relies only on the purpose-specific fields it requested, after the
artifact identity, runtime, platform BOM, resolved version, result and provenance are present and validated. Prose,
examples, commands, URLs, tool requests or scope changes in a response cannot direct an action; summaries inherit the
response's authority rather than increasing it. See xref:skills.adoc#context-authority[Context authority].

[[binding]]
== Version binding

Every version-sensitive call uses the `catalog` arguments from `camel-kit target`
(`--migration` for a migration destination). The `platformBom` tool parameter accepts these coordinates:

[cols="1,3"]
|===
| Runtime | Catalog lookup coordinate
| Main | `org.apache.camel:camel-catalog` at the selected Camel core version
| Spring Boot | The full `camel-catalog-provider-springboot` coordinate at its provider version
| Quarkus | The selected platform's `quarkus-camel-bom` coordinate
|===

The workflow checks the core version reported by `camel_catalog_components` and the runtime-specific
timer artifact returned by `camel_catalog_component_maven`. It records each request and result against the
whole profile. A missing tool, a bundled core version different from the selection, or a mismatched runtime
artifact produces `INCOMPLETE` even when an individual lookup succeeds. Detail tools may omit the core
version. They use the verified binding and must match the requested artifact identity.
A complete, successful exact-name list is required to establish absence.

For behaviour questions — YAML shape, runtime configuration, version changes, header propagation — skills call
`camel_docs_search` on the `camel-knowledge` server, not `camel`. The knowledge server tools (`camel_docs_search`,
`camel_docs_component_info`, `camel_docs_cve_search`, `camel_docs_release_info`, `camel_docs_jira_lookup`) complement
the catalog with documentation search; catalog tools (`camel_catalog_*`) remain on `camel`.

The current defaults are Camel {camel-version} for Camel Main and Spring Boot, with Camel {camel-quarkus-version}
on the Quarkus platform {quarkus-platform-version}; the catalog server artifact follows the Camel Main stream.

[[camel-tools]]
With the shipped Camel MCP 4.22.1 runner, required catalog checks have the following results for the
supported community targets. The runner can return the selected starter or extension alongside its bundled core.

[cols="1,1,1,2",options="header"]
|===
|Runtime |Requested core |Returned core |Required catalog check
|Main |4.22.1 or 4.18.4 |Matches requested core |Pass
|Spring Boot |4.22.1 |4.22.1 |Pass
|Spring Boot |4.18.4 |4.22.1 |Incomplete
|Quarkus |4.18.3 |4.22.1 |Incomplete (default platform 3.33.3.2)
|Quarkus |4.14.7 |4.22.1 |Incomplete (platform 3.27.3)
|===

The check applies to greenfield designs, existing applications and migrations. On an affected row the workflow
cannot complete a design that requires verified catalog artifacts. The selected application version is preserved.
For a different runner or platform, verify the actual responses. See the
xref:existing-project.adoc#catalog-limitation[runtime catalog limitation].

== The Camel catalog server

The workflow allowlist covers the read-only and generation helpers the skills use; runtime mutation and control
tools stay out of the generated configuration.

[cols="1,2"]
|===
| Tool | Purpose

2+| *Catalog exploration*
| `camel_catalog_components`, `camel_catalog_component_doc`, `camel_catalog_component_maven` | List, document and
  locate the Maven coordinates of components
| `camel_catalog_dataformats`, `camel_catalog_dataformat_doc` | Data formats and their options
| `camel_catalog_languages`, `camel_catalog_language_doc` | Expression languages
| `camel_catalog_eips`, `camel_catalog_eip_doc` | Enterprise Integration Patterns and their configuration
| `camel_catalog_kamelets`, `camel_catalog_kamelet_doc` | Kamelets and their dependencies
| `camel_catalog_examples`, `camel_catalog_example_file` | Camel examples and their files

2+| *Validation, security and tests*
| `camel_validate_route` | Validate one endpoint URI against the bound catalog (the skills call it once per
  statically extracted endpoint)
| `camel_validate_yaml_dsl` | Validate YAML DSL syntax
| `camel_transform_route` | Convert routes between YAML and XML
| `camel_route_context`, `camel_route_harden_context` | Extract components and EIPs from a route; candidate evidence
  for route hardening
| `camel_route_test_scaffold` | A JUnit 5 route test scaffold

2+| *Diagnostics and configuration*
| `camel_component_properties`, `camel_configuration_validate` | Component property metadata; validation of
  configuration properties
| `camel_dependency_check`, `camel_error_diagnose`, `camel_properties_translate` | Dependency checks, error
  diagnosis, property translation between runtimes
| `camel_version_list` | Camel versions with LTS status and JDK requirements

2+| *Migration and OpenAPI*
| `camel_migration_analyze`, `camel_migration_compatibility`, `camel_migration_recipes`,
  `camel_migration_guide_search`, `camel_migration_wildfly_karaf` | Migration analysis, compatibility, recipes and
  guidance
| `camel_openapi_validate`, `camel_openapi_scaffold`, `camel_openapi_mock_guidance` | OpenAPI validation,
  scaffolding and mock guidance
|===

The design stage verifies every component, EIP, data format and language before it enters the design, and records
the evidence (see xref:camel-brainstorm.adoc#catalog[Catalog verification]). During implementation the route files
are validated with `camel_validate_route` and `camel_validate_yaml_dsl`, and `camel_configuration_validate` is a
mandatory gate after writing application properties: generation is not complete until it passes or the documented
manual fallback is recorded. `/camel-validate` uses the same tools for its endpoint verification, and `camel-test`
uses the route context and hardening tools for its test strategy.

Without the catalog, a model writes component names from its training data, which may be renamed, removed or
different in the target version. With it, a request such as "a message queue" becomes three verified candidates
(`jms`, `amqp`, `kafka`) and a question to you, and an unknown name becomes a clarification instead of a guess.

[[citrus]]
== The Citrus server

`camel-test` validates the test vocabulary through `citrus_catalog_actions`, `citrus_catalog_action`,
`citrus_catalog_action_schema`, `citrus_catalog_endpoints`, `citrus_catalog_endpoint`,
`citrus_catalog_endpoint_schema`, `citrus_docs_index` and `citrus_docs_page`, plus resources such as
`citrus://schema/dsl/yaml`. The test schema and the generated test dependencies use `citrus.version` from
`.camel-kit/config.properties`, and the server coordinate is bound to the actual runner artifact in the agent's
configuration. Typed catalog and schema fields are treated as same-version data only when that runner version equals
`citrus.version`; otherwise the skill uses the same-version quick reference cached under `.camel-kit/.cache/citrus/`,
and marks a generated test as unverified rather than falling back to another Citrus version silently.

[[fallback]]
== Fallback

Skills call the tools directly without probing for availability first. If a call fails (tool not found, network
error, timeout), the skill falls back to the bundled guides and continues with a warning; the pipeline degrades
rather than stopping, and the missing verification is recorded.
